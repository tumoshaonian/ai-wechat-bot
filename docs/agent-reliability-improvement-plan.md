# 微信电脑 Agent 稳定性修改计划

日期：2026-09-05
状态：用户已批准，分阶段实施中。实际进展与未完成项见 [实施记录](agent-reliability-implementation.md)。

2026-09-10 范围澄清：目标是应用无关的电脑 Agent，不是预置软件机器人。本文出现的豆包、B站均为回归样例，不是软件白名单或专用产品需求。

## 一、目标与边界

目标是让自然语言任务完整进入 Harness，由 AI 理解意图和规划步骤，由程序保证授权、准确执行、可验证结果和可靠交付。

本次优先解决：复合任务误匹配文件、上下文缺失和重启恢复、主窗口不可交互、错误的完成汇报、交付结果不可追踪，以及任务取消与恢复边界。

原则：

- 移除自然语言关键词文件分流，不移除文件搜索工具及程序级安全校验。
- 正常聊天和电脑任务使用同一 Agent 入口；明确的停止、状态、新会话命令保留独立控制通道。
- 不因执行失败而抹掉已确认的对话事实；不因恢复历史而自动重做有副作用的动作。
- 不擅自用网页替代用户明确指定的客户端，不用进程启动或文件存在代替整个任务成功。
- 暂不解决同一桌面上人工操作与机器人操作的焦点竞争，但仍校验目标窗口身份。
- 不承诺任意软件、锁屏、安全桌面、登录验证等场景都可自动完成；能力不足时明确停止位置。
- 当前阶段沿用 Java 管理面、Python Bridge、Harness 和桌面执行器，不开展无关重构。
- 工具按能力划分：发现应用、准备窗口、观察控件或截图、定位、输入、调用动作、验证、导出成果、交付。应用专用适配是可选增强，通用流程不得以它存在为前提。
- “面向所有应用”是扩展目标，不是无条件兼容承诺；受控视觉能力也不能绕过登录、人机验证、安全桌面或权限限制。当前不可操作时报告具体缺口，不断言整个软件永久不支持自动化。

## 二、预期执行链路

消息接收与鉴权 → 会话加载 → Harness 理解与规划 → 受控工具执行 → 结果验证 → 文件交付 → 交付回执进入上下文 → 最终回复与任务归档。

贯穿全程的能力：任务标识、事件日志、取消信号、超时、权限校验和恢复检查点。停止命令不排在正在运行的普通消息后面。

## 三、实施阶段

### 阶段 0：建立可复现基线

改动与检查：

- 固定实际使用的 Harness 版本、运行二进制、SDK profile 和覆盖配置，确认源码能力与运行版本一致。
- 对照现有测试、日志和数据库，补充已发现问题的复现用例；记录原始失败结果。
- 确认 SDK 的恢复、上下文压缩、运行时事件注入及取消接口，不按接口名称猜测支持情况。
- 保存配置和数据库备份；不删除历史会话或用户文件。记录升级和回滚步骤。

交付物：基线测试、问题清单、接口能力核对结果。

验收：能够稳定复现复合请求被识别成 `豆包.lnk`、文件交付上下文缺失、窗口最小化恢复缺口等问题。需要真实 GUI 的场景与纯单元测试明确区分。

### 阶段 1：统一自然语言入口

改动：

- 删除 `UnifiedAgentBackend` 对自然语言文件请求的提前返回分支，移除不再使用的 `DesktopFileRequestResolver` 及其调用。
- 所有普通自然语言请求完整传给 Harness，不先抽取关键词、不擅自拆掉前置步骤。
- 文件名搜索作为 Agent 可调用的工具能力保留；遇到重名、目标不明或输出格式不明时，由 Agent 结合上下文判断或询问。
- `stop`、`end`、`status` 保留确定性处理；明确写明 `end` 是新会话边界，不是删除历史。
- `/文件` 等旧入口如保留兼容，也走统一的交付记录与结果回写链路，不再成为上下文盲区。
- 授权信息绑定任务，工具执行时仍强制检查权限，不只依赖提示词。

主要范围：`adapters/unified_agent.py`、`file_requests.py`、相关路由与测试。

验收：原始“打开豆包生成故事文档再发给我”请求完整进入 Harness，不因桌面存在 `豆包.lnk` 而提前发送；简单自然语言发送已有文件仍可完成。

### 阶段 2：建立可靠的文件交付与事件回写

改动：

- 为 Harness 提供结构化文件交付能力，由 Agent 选择成果；具体通过现有 MCP 或 SDK 扩展接入，在阶段 0 核实后确定。
- 使用可信任务上下文绑定微信连接、会话和接收对象，模型不能随意改收件人。
- 交付前校验授权、文件类型、存在性、大小及平台限制；目录不能作为普通文件直接发送。
- 将“成果已生成”和“交付已成功”分别记录。发送回执进入 Agent 可见历史，而不只写管理后台日志。
- 记录交付 ID、任务 ID、成果版本或摘要、尝试次数和结果；同一次交付重试去重，用户明确再次索取不受旧任务去重影响。
- 网络中断且不能确认结果时标记为“交付结果未知”，不能直接认定成功或盲目重发。
- 移除“自动合并全部桌面截图”的行为，只交付明确选中的最终成果。原有文件标签如临时保留，必须汇入同一交付服务。
- 限制无界输出：文件全文、巨型 UI 控件树和截图数据不自动塞入上下文，保留必要摘要及引用。

主要范围：`application.py`、`adapters/deepseek_harness.py`、文件发送适配器、事件记录与桌面 MCP 集成。

验收：生成成功但上传失败被报告为部分完成；追问“刚才发了什么”能得到与真实交付一致的回答；不混发中间截图；重试不重复执行生成任务。

### 阶段 3：上下文预算、会话恢复与隔离

改动：

- 核实实际 SDK profile 是否加载 token 计量与 `compaction-basic`，验证压缩事件，而不是只增加环境变量。
- 按实际模型容量配置压缩阈值、近期保留预算及摘要输出预算，给系统提示、工具、输出与推理留余量。输入上下文预算与 `HARNESS_MAX_TOKENS` 输出限制分开管理。
- 使用“较早历史摘要 + 近期完整对话 + 当前任务事实”；摘要保留目标、用户限制、项目路径、成果引用、已完成步骤及未决事项。
- 不按字符或任意消息数量截断历史，不拆散工具调用与结果；完整审计记录独立保存，压缩不删除原始记录。
- 修复冷启动历史加载：优先使用版本中已验证的恢复接口；若 SDK 入口缺少恢复，评估最小上游适配与本地受控历史重建，再确定方案。不得把同名 `create` 当作 `resume`。
- 历史重建若使用摘要而非原始恢复，明确标识恢复方式及信息损失，避免把历史命令当成新指令重新执行。
- 按微信连接身份、聊天类型、聊天 ID 和逻辑会话代次隔离上下文；数据库映射与重复消息检测使用一致命名空间。
- 原有会话编号迁移显式处理，不直接覆盖历史或静默重置。
- 普通失败保留事实和失败原因；取消记录已产生的效果；`end` 创建不继承旧上下文的新逻辑会话。

主要范围：`session_registry.py`、`adapters/deepseek_harness.py`、`config.py`、Harness 覆盖配置及后台相关配置。

验收：同会话连续追问、成功交付后追问、失败后追问、重启后续聊均保留正确事实；`end` 后旧上下文不自动进入新会话；不同连接不串话；压缩测试不丢失关键路径和待办步骤。

### 阶段 4：通用目标窗口准备能力

改动：

- 引入结构化的窗口诊断与准备能力，不只给豆包增加特殊判断。
- 联合进程身份、程序路径、窗口句柄、所有者关系、标题及窗口尺寸识别主窗口；辅助窗口和托盘窗口不能被当成可交互主窗口。
- 区分未启动、最小化、隐藏、屏幕外、加载中、不可访问、需登录等状态；状态不明确时不随便操作其他窗口。
- 对已确认的目标窗口执行恢复，必要时移动到有效显示区域；等待有截止时间的就绪条件。
- 重新校验窗口身份、可见性、尺寸和可交互性，然后查找输入控件。窗口句柄失效时重新定位，不能沿用旧目标。
- 优先恢复窗口，不默认杀进程重启；可能丢失未保存内容的重启需要额外判断或用户确认。
- 返回结构化证据和错误码，例如主窗口未找到、恢复失败、控件不可访问、需要登录，而不是统一“任务失败”。

主要范围：`scripts/windows_uia.ps1`、Python 桌面 worker、MCP 工具声明及相关测试。

验收：正常、最小化、屏幕外和辅助窗口共存情况下能识别正确目标；恢复失败不输入；豆包可交互时完成提问与截图；不会操作无关程序。锁屏与登录障碍清楚报告。

### 阶段 5：任务状态、验证、取消和有限恢复

改动：

- 分离任务状态与对话记忆，记录关键阶段：排队、执行、等待确认、交付、成功、部分完成、失败、取消，以及必要的结果未知状态。
- 基于工具证据验证动作：启动有目标窗口证据；提问有提交证据；截图属于目标任务；文件交付有发送接口回执。回执不表述为用户已读。
- 把用户明确指定的目标应用和输出要求记录为任务约束；修改执行方式不能静默覆盖原要求。
- 进度来自真实阶段事件，如“已恢复豆包，正在定位输入框”，不只定时输出已耗时秒数。
- 按错误类型设置恢复动作和重试上限。窗口未就绪可等待或恢复，登录问题暂停；对提交结果未知的动作先检查，不能盲目重复。
- 打通 Bridge、Harness、桌面 worker 及所属子进程的取消；只结束本任务拥有的执行器，不误杀其他任务或用户应用。
- 实际停止确认前显示“正在停止”；无法确认时保留诊断，不把取消请求等同于取消成功。
- 分开处理执行失败与微信回复通道失败：保留执行结果和交付状态，防止通道故障触发整项任务重做；长任务的通道恢复方案以平台实际能力为准。
- 多会话可独立接收、查询、取消；桌面写操作保持串行，不因此引入同桌面并发操作。

主要范围：`application.py`、Harness backend、桌面 worker、任务事件和后台任务详情。

验收：执行中停止后没有残留工具动作；任务超时可定位具体阶段；回复失败不重做有副作用的步骤；一个会话失败不会误取消另一个会话。

### 阶段 6：通用应用操作与受控视觉后备（独立能力阶段）

前置条件：前五阶段通过；确认可用视觉模型、调用成本、截图传输与隐私范围。若需新凭据、额外付费服务或平台接入，先由用户确认。

改动：

- UIA 或应用接口可用时优先使用；用户要求网页时使用浏览器能力。
- Harness 根据原始目标选择应用及操作序列，不按软件名硬编码任务分流。保留主窗口身份与用户指定的应用约束；已有专用适配可选使用，但不能代替通用能力。
- 观察输出使用统一的窗口、控件、操作结果和证据结构。控件可访问时使用结构化工具；控件不可访问且已配置视觉能力时，在同一目标窗口上进入视觉观察闭环。
- 对客户端不可访问控件探索结构化的“截图观察 → 目标定位 → 受控输入/点击 → 重新观察”工具，不开放无限制临时键鼠脚本。
- 文档生成／导出是通用成果任务：执行用户指定应用中的生成或编辑，定位可用导出方式，处理保存对话框，验证路径、格式和内容，再进入统一交付服务。不使用快捷方式、空文件或机器人自行代写的内容冒充应用导出结果；需要替代方案先确认。
- 限制目标窗口、动作次数、总耗时及输入范围；画面发生变化时重新定位，不复用过期坐标。
- 将页面文字、文档和工具返回内容视为任务数据，不能让其中的指令覆盖用户目标或扩大文件发送权限。
- 客户端不可执行时如实报告；要改用网页，按用户既定偏好或明确确认执行，并保留差异说明。

验收：选择至少三类真实应用（原生控件应用、内嵌网页客户端、自绘／不可访问控件应用），验证通用观察、定位、操作与验证机制。加入未预置适配的软件，确认无需增加软件名分支即可尝试通用操作；对不可支持的状态明确停止。B站客户端搜索仅是其中一个样例，不能用浏览器成功替代客户端验收。通用文档导出至少跨两种编辑或生成应用验收；豆包只是可选样例。视觉定位失败不随意点击其他区域。

## 四、后台与可观测性配套

随上述阶段逐步增加，不另起一轮后台重写：

- 会话详情：连接归属、逻辑会话代次、恢复方式、最近压缩事件及可获得的上下文用量。
- 任务详情：当前阶段、最后有效进度时间、错误码、工具调用证据、取消状态。
- 文件详情：成果来源、选中交付原因、交付尝试、成功/失败/未知状态。
- 配置：上下文策略、工具超时、有限重试策略、能力开关。非法配置拒绝保存或拒绝启用。
- 日志与界面隐藏密钥等敏感内容；工具响应和模型输出不无界写入日志。

## 五、测试与完成标准

测试分三层，不能用单元测试通过代替真实任务通过：

1. 单元测试：入口不截断、权限检查、会话隔离、压缩策略校验、状态流转、交付去重、窗口选择。
2. 集成与故障注入：SDK 重启恢复、模型/工具超时、微信发送失败、回执未知、取消传播、并发会话隔离。
3. Windows 与企业微信端到端测试：用独立测试会话和临时文件验证下面的用户场景，保留任务 ID、日志及结果证据。

必须验收的场景：

- 普通聊天后追问，保持语义连续。
- 自然语言索取已有文档，不需要输入 `/文件`。
- 请求豆包生成文档再发送：有能力时完成完整链路；能力不足时报告未完成步骤，绝不发送快捷方式冒充成果。
- 发送成功、失败或未知后追问，回答与实际结果一致。
- 重启后继续修改“刚才的项目”；发送 `end` 后不自动继承该项目上下文。
- 长对话触发压缩后仍记得任务约束、关键路径和交付状态。
- 豆包最小化或主窗口在屏幕外时，恢复后提问并截图。
- 指定 B 站客户端搜索，不静默换成网页，不附带无关截图。
- 执行中 `stop`、任务超时、微信通道失败均不会留下继续操作或整项任务重复执行。
- 不同微信连接和会话之间不共享错误记忆或互相取消。

重复执行要求：关键正常路径与最小化恢复路径在受控条件下各连续验证至少 3 次，记录每次结果。这是最低回归门槛，不等于对所有软件状态的稳定性保证。

完成报告逐项列出：已通过、失败、因环境或权限无法测试；未经真实测试的能力不得写成已完成。测试不使用用户重要文件，不自动安装软件、重启电脑或清除原会话记录。

## 六、交付顺序与审阅事项

建议按阶段 0 → 1 → 2 → 3 → 4 → 5 → 6 执行，每阶段保留独立改动和验收结果。阶段 1—5 是当前稳定性修复，阶段 6 是进一步支持不可访问客户端控件的能力扩展。

需要审阅的策略选择：

- 是否认可明确控制命令保留程序处理，普通自然语言统一交给 Harness。
- 是否认可“压缩摘要 + 近期完整上下文”，不使用简单最后 N 条截断。
- 是否认可客户端改网页需要说明并按用户授权决定，默认不静默替换。
- 是否认可视觉能力单独验收，必要的新模型、成本或权限另行确认。

本计划已经批准；提交或推送远程仓库另按用户授权执行。
